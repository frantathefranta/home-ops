#+title: app-template compliance audit
Audit of all 41 apps under =kubernetes/apps/= that deploy the
=bjw-s-labs/helm/app-template= chart (v5.1.0, uniform — no chart version
drift) against the conventions in =.agents/skills/add-app/SKILL.md=.
35 are enabled; 6 are disabled (commented out in their namespace
kustomization — see Not fixed). Baseline apps: media/maintainerr,
default/vikunja, default/bar-assistant.

* Status
All violations below were found in the initial audit and then fixed in
follow-up commits on this branch (digest pinning, lean =ks.yaml=,
reloader annotations). Re-running the same checks reports zero
violations.

** Not fixed (out of scope)
6 apps are disabled — commented out in their namespace
=kustomization.yaml=: =default/oxidized=, =default/vikunja=,
=home-automation/birdnet=, =home-automation/music-assistant=,
=observability/gatus=, =observability/kromgo=. =flate build= only
discovers Kustomizations registered in the tree, so these fail to
build locally with "no Kustomization named ..." — the same reason
explains the "pre-existing" build failures. Uncommenting them to
re-enable is a user decision, not a convention fix. All fixes in
this branch were still applied to their files so they conform if
re-enabled. (Also: =default/oxidized= still declares its own
=decryption: provider: sops= block instead of relying on
=components/common=.)

* Conforming
Conformance checks that pass across all 41 apps:
- chart pinned to app-template =5.1.0= everywhere
- all ExternalSecrets use =akeyless-secret-store= (no 1Password remnants)
- no volsync references (kopiur migration complete)
- all app-template routes reference =internal=/=external= gateways in
  =kube-system= (the two =envoy-*= parentRefs live in the forgejo and
  victoria-logs charts, which are not app-template)
- all 35 enabled apps are registered in their namespace
  =kustomization.yaml=; the 6 disabled ones are commented out
