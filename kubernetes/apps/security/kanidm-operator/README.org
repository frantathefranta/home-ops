#+title: Kanidm

* First rollout

Before switching TREK to Kanidm:

1. Verify DNS and TLS from both a browser and TREK.
2. Take a recoverable TREK backup and verify that email addresses in the private
   provisioning repository match the existing TREK users. Matching usernames alone
   does not preserve accounts.
3. Confirm credential PushSecrets have synchronized before completing enrollment.
   Keep independent access to Akeyless for disaster recovery.
   Treat enrollment links as credentials; do not publish them in logs or Git.
4. Retrieve each user's enrollment link from the ~TokenCreated~ event:

   #+begin_src sh
   kubectl -n security describe kanidmpersonaccount <account>
   #+end_src

5. Give each link only to its intended user and enroll a passkey before reconciling
   TREK. Provisioning does not wait for individual users to enroll credentials.
6. Log in as the existing TREK users. Confirm their user IDs, roles, trips, and
   sharing are preserved. Confirm a person outside the access group cannot start
   a new login.

Choose the permanent Kanidm origin before enrolling users. Changing it afterward
breaks their WebAuthn credentials.

If the previous ~kanidm-identities~ Kustomization has already reconciled in your
cluster, set its ~spec.deletionPolicy~ to ~Orphan~ before removing it. Otherwise
deleting the old Kustomization can prune the person and group resources it owns.

* Moving OAuth resources between Kustomizations

Before deploying the consolidation of the five old OIDC Kustomizations, orphan
their inventories. Deleting them with the default pruning policy can delete the
OAuth clients and their generated credentials before the applications adopt them.
Run these commands against the existing cluster before merging the move:

#+begin_src sh
for app in trek lubelog paperless tandoor; do
  kubectl -n default patch kustomization "$app-oidc" --type=merge \
    -p '{"spec":{"deletionPolicy":"Orphan"}}'
done
kubectl -n observability patch kustomization grafana-oidc --type=merge \
  -p '{"spec":{"deletionPolicy":"Orphan"}}'
#+end_src

Verify all five old objects report ~spec.deletionPolicy: Orphan~. Record the
OAuth client and generated Secret UIDs before the move, then verify they remain
unchanged after adoption and that the application Kustomizations become Ready.
This is an ownership transfer, not a client recreation or credential rotation.

Rollback is another ownership transfer: do not blindly revert with pruning
enabled. First annotate the moved OAuth clients and PushSecrets with
~kustomize.toolkit.fluxcd.io/prune: disabled~, restore the split configuration,
and wait for the old OIDC Kustomizations to adopt them. Remove the temporary
annotations only after their ownership labels identify the restored owners.

* Identity administration

Make person and membership changes in the [[https://git.franta.us/franta/kanidm-provision][private provisioning repository]].
Treat write access to that repository as identity-administration access. Review
removals carefully: reconciliation can delete accounts and revoke memberships.

* Existing TREK accounts

TREK 4.3.3 first matches ~(oidc_sub, oidc_issuer)~, then case-insensitive email.
For an already OIDC-bound account it replaces the old binding on the same user
row. That replacement branch does not require ~email_verified~. Keep primary
emails administratively controlled; do not grant application users
~idm_people_self_mail_write~ or broad identity-administration rights.
See [[https://github.com/liketrek/TREK/blob/1c05ee4b3ac9523c41ccdd3baad989ba48a7409a/server/src/nest/oidc/oidc.service.ts#L624-L648][the pinned TREK account-linking implementation]].

* Recovery

Kaniop's backup/restore subsystem is experimental and not production-supported.
File-stability checks do not prove that an online backup finished writing. Verify
an off-cluster restore into an isolated target before relying on this mechanism;
a healthy Schedule alone is not proof of recoverability.

Preserve the original backup encryption key for as long as its backups are needed.
Do not regenerate it during recovery: a new key cannot decrypt existing backups.
Keep independent access to Akeyless outside the cluster.
Git declarations do not reconstruct enrolled credentials or the identity database.

Native manual backup and restore require a stopped server and the same Kanidm
version that created the backup. In 1.11.2 the default manual backup is gzip,
even if the supplied filename ends in ~.json~. Preserve the ~.json.gz~ suffix so
restore selects the correct decoder. For a stopped instance with its config and
volumes mounted:

#+begin_src sh
kanidmd database backup -c /data/server.toml /backup/kanidm.backup.json.gz
kanidmd database restore -c /data/server.toml /backup/kanidm.backup.json.gz
#+end_src

Authelia and glauth are retired. Restoring an application's old provider settings
does not restore its former identity provider. Recover the pre-retirement service
manifests, Authelia database, and original encryption/signing keys before attempting
an old-provider rollback. Preserve Kanidm and existing application users and data.

* Retired identity services

Before removing the legacy services, verify a final recoverable Authelia database
backup and retain its original storage-encryption and signing keys. The removal
prunes Authelia's PostgresCluster and Dragonfly resources, not just its web pods;
operator-managed database volumes may be deleted. Do not rely on a Git revert to
recover that data. Do not delete off-cluster backups or Akeyless recovery secrets.

Confirm no external LDAP or forward-auth clients still depend on these services.
Unlike the OAuth ownership transfer above, retirement intentionally uses pruning,
not Orphan, so the old workloads actually leave the cluster.

Disable any persisted Authelia authentication source in Forgejo's Site
Administration -> Authentication Sources. Removing Helm configuration alone
does not remove that database record. Retain the working Kanidm source and
independent SSH access.

Vikunja is disabled in the namespace configuration. Its inactive legacy
authentication configuration is unchanged and must be replaced before re-enabling
that application.

* Migrating existing application accounts (historical cutover procedure)

Back up the application's database and files before cutover. Privately record
local user IDs, permissions, ownership, and external-login associations. Matching
email addresses alone is not a general account-preservation guarantee.

For Paperless and Forgejo, sign into the existing account first, then connect
Kanidm: Paperless's My Profile or Forgejo's Settings -> Security. Test a fresh
Kanidm login and verify the same local user ID and permissions. Do not create
replacement users or disconnect Authelia before the new connection works.

Tandoor needs a single-provider cutover, not two configured OIDC providers.
Before switching, establish and test local-password login on the existing
accounts. If necessary, set a password interactively on an existing user:

#+begin_src sh
kubectl -n default exec -it deploy/tandoor -c app -- /opt/recipes/venv/bin/python /opt/recipes/manage.py changepassword <existing-username>
#+end_src

After switching the configured provider to Kanidm, use local login on the same
account, then connect Kanidm from user settings. Verify a fresh Kanidm login has
the original user ID, Space memberships, and recipe access. Retain old Authelia
associations for rollback; do not delete users or change ownership. Local login
does not require both OIDC providers to be configured. Retire temporary normal-user
passwords after successful migration, keeping protected administrator recovery.
Email-based automatic linking is unnecessary for this procedure. Tandoor's signup
form is not a registration prohibition. An Authelia rollback now also requires
recovering the retired identity services; provider settings alone are insufficient.

Forgejo administrator status is synchronized from the configured group claim at
login. Group values must match exactly, including underscores and the SPN domain;
an absent or mismatched administrator group can remove administrator status.
Keep recovery access while changing group policy. Group removals do not terminate
existing application sessions immediately. Merge the private provisioning change
and allow its groups to reconcile before testing the new Forgejo authorization.

LubeLogger matches existing accounts by exact email, including case. Check its
root-user email mapping separately. Persisted ~userConfig.json~ and
~serverConfig.json~ can override environment settings; check them if old OIDC
configuration persists after rollout. Its registration-disable flag only blocks
the registration UI: existing valid invitation tokens remain usable.

Grafana's temporary email lookup was removed after subject bindings migrated.
Keep primary emails administratively controlled and verify fresh logins resolve
through the persisted Kanidm subject rather than re-enabling email-based lookup.

Preserve local application users, their ownership, and existing identity links.
Retired identity-service removal is not an application-account deletion.

Grafana's Generic OAuth subject binding now refers to Kanidm. Provider rollback
requires a working restored identity provider and the corresponding captured
bindings, not only a change of endpoint URLs. A database restore can discard
intervening changes.
